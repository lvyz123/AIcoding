## 一、LSF 适配架构评估

七个阶段的 CLI 路由、manifest 哈希校验、shard 产物结构都设计正确，`run_shard_stage` 真正实现了分布式（每个 job 约 50 MB），这是 v2 LSF 的核心价值。但对照实际数据量做定量分析后，有三个阶段存在**单机全量加载瓶颈**，在 12 GB laptop 上仍有 OOM 风险，在 LSF 集群上则是单点瓶颈。

---

## 二、各阶段内存评估（基于实际日志数据）

| 阶段 | 设计 | 实际峰值估算 | 12GB可用(9288MB) |
|------|------|------------|-----------------|
| `prepare` | 轻量，只建索引+写 seeds | ~400 MB | ✅ 安全 |
| `run-shard` | 真分布式，1/N seed | ~50 MB/shard | ✅ 安全 |
| **`merge`** | **全量 marker + candidates + coverage_eval** | **~6,100 MB** | ⚠️ 有压力 |
| **`prepare-coverage`** | **全量 marker + candidates + 写 bundle** | **~6,100 MB** | ⚠️ 有压力 |
| `run-coverage-shard` | source 分布式，但 target_bundles 全量 | ~3,700 MB | ⚠️ 有压力 |
| `merge-coverage` | 只加载 CSR metadata + 懒加载 bitmap | ~500 MB | ✅ 安全 |

**`merge`（普通路径）是最大问题**：它在单个进程里加载所有 426k marker records（2,481 MB）+ 生成所有 1.4M candidates（3,578 MB）+ 运行完整的 coverage_eval（还有 donut cache 风险），总峰值超过 6 GB。这条路径的内存消耗与 v1 单机运行完全等价，分布式架构对它没有任何帮助。

**`prepare-coverage` 同样问题**：先加载全量 marker records，再生成全量 candidates，再写入 bundle 文件，峰值内存与 `merge` 相同。区别是它不运行 coverage_eval，但内存压力仍然很高。

**`run-coverage-shard` 的 target_bundles 问题**：`load_candidate_bundle_buckets_for_candidates` 按 source candidates 的 shape_key 加载对应的 target bucket。由于所有 clip 都是 135×135 px（同一工艺节点、同一 clip_size），所有 candidates 的 shape_key 相同，这意味着每个 coverage shard job 都需要加载**全量 1.4M candidates 的 bundle**（约 3,578 MB）。分片只减少了 source 侧的数量，没有减少 target 侧。

---

## 三、具体问题定位

**问题一（最严重）：`merge` 路径没有实现分布式 coverage**

`merge_stage` 直接调用 `evaluate_candidate_coverage(candidates, exact_clusters, config)`，这是 v1 的非分布式路径。对于大版图，应该调用分布式的 `prepare-coverage` + `run-coverage-shard` + `merge-coverage` 路径，而不是在 merge 里一次性运行。当前的 `merge` 阶段实际上是个"退化为 v1" 的单机路径，适合小 crop 验证，但不适合 550um×550um 的全版图。

**问题二：`run-coverage-shard` target_bundles 全量加载**

所有 clip shape 相同时，target_bundles 就是全量候选。需要在 source shard 内进一步筛选哪些 target 需要加载（例如只加载 fill_bin 相近的 target bucket），而不是把所有 shape 匹配的 target 全部载入内存。

---

## 四、修复方案

**修复一：`merge` 路径改为自动选择分布式**

对于 exact_cluster 数超过阈值的情况，`merge_stage` 应自动转发到 `prepare-coverage` + `run-coverage-shard` + `merge-coverage` 路径，而不是内嵌单机 coverage_eval：

```python
MERGE_DISTRIBUTED_THRESHOLD = 20000  # exact_cluster 数超过此值走分布式

def merge_stage(manifest_path, output_path=None):
    ...
    exact_clusters = group_exact_clusters(marker_records)
    if len(exact_clusters) > MERGE_DISTRIBUTED_THRESHOLD:
        raise RuntimeError(
            "exact_cluster=%d 超过阈值，请使用 prepare-coverage -> "
            "run-coverage-shard -> merge-coverage 路径" % len(exact_clusters)
        )
    # 小数据量才走单机路径
    ...
```

**修复二：`run-coverage-shard` 按 fill_bin 分桶加载 target**

在 `prepare-coverage` 阶段，target bucket 已经按 `(shape_key, fill_bin)` 两级分桶存储。`run-coverage-shard` 时，source 候选按 fill_bin 排序，只加载 fill_bin 在 `[source_min_bin - FILL_BIN_RADIUS, source_max_bin + FILL_BIN_RADIUS]` 范围内的 target bucket，而不是同 shape 的全量：

```python
# run_coverage_shard_stage 里替换：
source_fill_bins = set(
    int(coverage_fill_bin_for_bitmap(c.clip_bitmap)) for c in candidates
)
bin_min = min(source_fill_bins) - COVERAGE_FILL_BIN_NEIGHBOR_RADIUS
bin_max = max(source_fill_bins) + COVERAGE_FILL_BIN_NEIGHBOR_RADIUS

target_bundles = load_candidate_bundle_buckets_for_fill_range(
    manifest["candidate_bundle_index"], candidates, bin_min, bin_max
)
```

这把 `run-coverage-shard` 的 target 内存从"全量 3,578 MB"压缩到"source fill_bin 范围内的 target，约 200-500 MB/shard"，真正实现了 coverage 阶段的内存分布。

**修复三：`prepare-coverage` 流式写 bundle，不驻留全量 candidates**

当前 `prepare-coverage` 先生成全量 `all_candidates`（3,578 MB），再调用 `save_candidate_bundle_index`。改为按 exact_cluster 批次流式生成并写入，每批处理完后立即释放 bitmap：

```python
# 流式生成 candidates，按 fill_bin 分组写入 bundle bucket
for chunk_start in range(0, len(exact_clusters), PREPARE_COVERAGE_CHUNK_SIZE):
    chunk = exact_clusters[chunk_start : chunk_start + PREPARE_COVERAGE_CHUNK_SIZE]
    chunk_candidates = []
    for cluster in chunk:
        chunk_candidates.extend(generate_candidates_for_cluster(cluster, config))
    _append_candidates_to_bundle_buckets(chunk_candidates, bundle_root, config)
    # chunk_candidates 离开作用域，bitmap 被 GC 释放
```

这把 `prepare-coverage` 的峰值内存从 6,100 MB 压缩到约 2,500 MB（marker records）+ 一个 chunk 的 candidates（约 100 MB）。

## 五、对 LSF 集群适配需求的总结

`run-shard` 阶段完全满足 LSF 需求，是这个版本真正的亮点。但对 550um×550um 全版图，整体流程还需要走 `prepare-coverage → run-coverage-shard → merge-coverage` 路径，并配合上述三个修复，才能将所有阶段的单机内存控制在 3 GB 以内，真正适配 12 GB laptop 和 LSF 集群环境。
